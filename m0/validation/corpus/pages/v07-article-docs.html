createClient()

Creates a configured client instance. Call it once at process start and reuse the result — the client owns a connection pool and a token refresh timer.

Signature

The only required option is apiKey. Everything else has a default that is safe for production.

index.tsCopy
import { createClient } from "@emberline/sdk";

const client = createClient({
  apiKey: process.env.EMBERLINE_KEY!,
  region: "eu-west-1",
  timeoutMs: 10_000,
  retries: { attempts: 3, backoff: "exponential" },
});

// Reuse `client` for the lifetime of the process.
await client.send({ to: "ada@example.com", template: "welcome" });
One client per process

Creating a client per request works, but you lose connection reuse and each instance starts its own refresh timer. In a serverless runtime, hoist the client outside the handler.

Options

All options are read once at construction. Changing the object afterwards has no effect.

NameTypeDescription
apiKeyRequired string A live or test key from the dashboard. Keys prefixed sk_test_ are routed to the sandbox and never deliver.
regionOptional "eu-west-1" | "us-east-1" | "ap-northeast-1" Where payloads are processed and stored. Defaults to the region of the key. Cannot be changed after the first send without a data migration.
timeoutMsOptional number Per-attempt socket timeout in milliseconds. Defaults to 15000. The total wall-clock budget is roughly timeoutMs × attempts.
retriesOptional RetryPolicy See Retries. Defaults to three attempts with exponential backoff and full jitter.
fetchOptional typeof fetch Injects a custom fetch implementation. Useful for tracing, proxies, and tests. Must follow the WHATWG signature.
onRateLimitOptional (info: RateLimitInfo) => void Called before each backoff sleep with the remaining quota and reset time. Use it to emit a metric rather than to reimplement retrying.

Retries

The client retries on network errors, 429, and 5xx responses. It never retries 4xx other than 429, because those will fail identically on the second attempt.

Idempotency

Every request carries a generated idempotency key so a retried send cannot deliver twice. Supply your own with idempotencyKey when the retry crosses a process boundary:

retry.tsCopy
await client.send({
  to: user.email,
  template: "password-reset",
  idempotencyKey: `reset:${'$'}{user.id}:${'$'}{tokenHash}`,
});
Idempotency keys expire after 24 hours

A retry later than that is treated as a new send. If your queue can hold a message for longer, deduplicate before calling send().

Backoff

  1. Attempt 1 fails with 503.
  2. Sleep random(0, 250ms), attempt 2.
  3. Sleep random(0, 500ms), attempt 3.
  4. Throw DeliveryError with cause set to the final response.
Do not wrap send() in your own retry loop

Two layers of retry multiply, not add. A three-attempt policy inside a three-attempt loop is nine deliveries against a rate limit that is counting all of them.
